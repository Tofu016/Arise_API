# Production requirements and known gaps

What must be true before this API runs anywhere other than a developer's
laptop. `DEPLOY.md` is the step-by-step runbook; this file is the checklist
of settings and the list of things the code does **not** do yet. Keep it
current: when a setting or a gap changes, change it here in the same commit.

## 1. Must be set

### `.env` (copy from `.env.example`; never commit the real one)

| Key | Production value | Why it matters |
|---|---|---|
| `CI_ENV` | `production` | Anything else shows PHP errors and SQL to visitors. |
| `BASE_URL` | `https://<api-host>/` | Trailing slash. Must match what the front-end was built against. |
| `CORS_ORIGIN` | `https://<web-app-host>` | Exact origin, no trailing slash. Unset falls back to `http://localhost:5173`, so the real front-end is blocked and password-reset links point at localhost. One origin only. |
| `FRONTEND_URL` | blank, or the web app address | Only if it differs from `CORS_ORIGIN`. |
| `DB_HOST` | `localhost` | |
| `DB_USER` | a dedicated account, **not `root`** | See section 2. |
| `DB_PASS` | a generated password | Unset or blank falls back to an empty password. |
| `DB_NAME` | `arise_web` | |
| `UPLOAD_ROOT` | absolute path, trailing slash | Public tour images. |
| `PROTECTED_UPLOAD_ROOT` | absolute path, trailing slash | Blank falls back to two directories above `index.php`, which is rarely right on a server. |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` | the relay's real values | Without them the email queue never drains: password-reset and approval mail never leaves. |
| `SMTP_FROM_EMAIL`, `SMTP_FROM_NAME` | sender address and name | Quote names containing spaces. |
| `SENTRY_DSN` | leave blank | Nothing reads it yet. |

Every secret (`DB_PASS`, `SMTP_PASS`) is generated by whoever runs the
server. Never send a `.env` by email or chat, and never reuse a
development value.

### Not in `.env`: edit or configure by hand

- **`application/config/config.php`**: `$config['log_threshold']` is `0`,
  which logs nothing, including the upload errors the code reports through
  `log_message('error', …)`. Set it to `1` and keep `application/logs/`
  writable.
- **HTTPS.** Bearer tokens travel in the `Authorization` header, so
  without TLS they cross the network readable. Serve only over HTTPS and
  add HSTS.
- **`php.ini`**: `upload_max_filesize = 64M`, `post_max_size = 72M`,
  `memory_limit = 256M`, `max_execution_time = 120` (panoramas are up to
  30 MB). `display_errors` must be off.
- **Apache**: `mod_rewrite` on and `AllowOverride All`, so the root
  `.htaccess` can forward the `Authorization` header. Deny web access to
  `.env`, `.git`, `*.sql`, `*.md`, `composer.lock` and `protected-uploads/`
  (DEPLOY.md A7 and A8), and check with `curl -I`. Disable directory
  listing and PHP execution under `uploads/`.
- **Scheduled jobs** (DEPLOY.md A10 and A10b, CLI only): `processEmails`
  every couple of minutes, `purgeExpired` daily.
- **Backups** of the database, `uploads/`, `protected-uploads/` and the
  server's `.env`. The last three are not in git or in a DB dump.
- **First admin account** created by hand (`SEED.md`). Nobody can
  promote themselves.

## 2. Known gaps: decide or fix before go-live

These are real, and the code does not handle them today.

- **No rate limiting.** `Auth_API/login`, `register`, `forgotPassword` and
  `Feedback_API/submit` are public and unthrottled. Login can be
  brute-forced; the other three can flood the database and the email
  queue. Either add per-IP and per-account attempt limits in the API or
  throttle at the web server or firewall. Until then the only defence is
  the 8-character minimum password (`Account_policy`).
- **Registration is not verified.** `Auth_API/register` only checks that the
  address ends in `@sdca.edu.ph`. Nobody proves they own the mailbox, so
  anyone can register as any name at that domain. New accounts are
  `pending` and an admin must approve them, but the admin cannot tell a
  real student from an invented address. Either add an email-verification
  step before an account can be approved, or accept the risk and tell
  admins to check each approval against a real record.
- **The development DB user is `root` with an empty password.** That is the
  XAMPP default and only acceptable on a developer's machine. In production
  create an account limited to `SELECT, INSERT, UPDATE, DELETE` on
  `arise_web.*` (DEPLOY.md A5 grants `ALL PRIVILEGES`; tighten it to this).
  Use a separate account, used only by hand, for `ALTER TABLE`, and never
  give the app account `DROP`, `FILE` or `GRANT`.
- **`IndoorUploads_API/serve` is public.** Indoor photos are called
  "protected" but are streamed to anyone who knows the path. Either decide
  they are public and update the wording, or put an auth check back.
- **One CORS origin.** If the admin site and a public site will live on
  different origins, the code needs an allow-list.
- **No security headers** (`X-Content-Type-Options: nosniff` and the like)
  are sent by the API. Add them in Apache.
- **CodeIgniter 3.1.13** is the last CI3 release and supports PHP up to
  8.1. Test on the PHP version the server actually runs.

## 3. Housekeeping the code does for you

`php index.php Cron_API purgeExpired` deletes expired login tokens,
expired password-reset tokens, and emails sent more than 30 days ago
(`Cron_API::SENT_EMAIL_DAYS`). It never touches an unsent email, so a
failing email stays visible for diagnosis. Expired tokens are already
refused at login, so a missed run costs nothing but table size.

An admin cannot demote themselves or the last remaining admin
(`Users_API::updateRole`); they still cannot delete their own account.
